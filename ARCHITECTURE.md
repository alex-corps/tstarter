# Архитектура генератора

Генератор день за днём имитирует B2B-дистрибьютора автозапчастей и пишет результат в Postgres. Скрытая модель спроса хранится отдельно от рабочих таблиц, чтобы прогноз можно было строить только по «видимым» данным.

## Слои

```text
app.py, run_gen.py, user_orders.py     точки входа
        │
        ▼
gen/engine.py                          цикл одного дня
        │
        ├── sales, receipts, assortment, ordering, stock
        │
        ▼
public.*                               то, что видит аналитик
gen_internal.*                         скрытое состояние и «ответы»
```

Рабочие таблицы (`sale_order_day`, `income_order_day`, `income_day`, `rest_day`, `current_assortment`) не содержат параметров модели. Истинный спрос, включая потерянный при OOS, лежит в `gen_internal.truth_demand`.

## Порядок одного дня

`gen/engine.py`, функция `run`:

1. Остаток на начало = остаток на конец вчера (`load_last_stock`).
2. Продажи по SKU в статусе «активный» и «вывод». Больше остатка продать нельзя.
3. Приходы по заказам, у которых наступила `resolve_dt`. Остаток растёт после продаж.
4. Ассортимент: «ввод» → «активный» при первом приходе, закрытие вымытых «вывод», раз в месяц ротация и новинки.
5. Заказ. Поставщики из списка user считаются через `user_orders.calc_orders`, остальные — `ordering.order_day`.
6. Запись `rest_day` и строки в `gen_internal.calc_log`, затем `commit`.

Повторный запуск с той же «даты с» сначала удаляет факты начиная с этой даты (`db.rollback_from`) и считает их заново. Случайность задаётся seed, поэтому результат того же периода совпадает.

## Справочники и факты

Справочники генератор не создаёт, они приходят из `data/seed`:

- `dim_category`, `dim_products`, `dim_supplier`, `dim_customer`, `dim_product_crosses`
- `supplier_schedule` — явные даты заказов на 2025–2030
- `current_assortment` — 4000 активных SKU с 2024-01-01

`dim_products.supplier_id` определяет, кто поставляет SKU. Корневая категория для сезонности считается в `state.load_world`: у категории 3 уровня родитель родителя.

`sale_order` генератор не заполняет. Продажа — одна строка `sale_order_day` на день, клиента и SKU.

## Скрытый мир

`world.ensure_world` заполняет `gen_internal` один раз. Повторный запуск профили не меняет. `world.reset_world` стирает только таблицы `gen_internal` и собирает профили заново. Факты (`sale_order_day`, `income_day`, `income_order_day`, `rest_day`) она не трогает: их нужно очистить отдельно, иначе стартовый остаток останется от старого уровня спроса.

Профиль SKU (`sku_profile`): класс спроса `fast` / `intermittent` / `lumpy`, базовый дневной уровень `base_daily`, дрейф, ABC. Класс задаёт ритм в `DemandModel.order_batch`, уровень задаёт объём:

- fast — пуассон каждый день, низкий ADI. `base_daily = 1.0 + base * 2.0`, медиана порядка тысяч штук в год;
- intermittent — пачка примерно раз в 8 дней, ровный размер;
- lumpy — пачка примерно раз в 20 дней, размер сильно скачет.

Для intermittent и lumpy `base_daily = 0.2 + base * 0.6`: пол около 0.2 штуки в день, медиана порядка 150–180 штук в год. Нижние 10% по рангу Парето получают множитель 0.25 — это явные аутсайдеры, около 10% ассортимента, а не половина. `base` — Парето с показателем 1.3, из него же берётся ABC.

Сезон по корневой категории — словарь `SEASON` в `world.py`. Годовой сдвиг и «тёплая зима» — `year_anomaly`. Доли аналогов — `cross_share`, при OOS одного аналога 60% его доли перетекает на доступные (`sales.sell_day`).

Профиль поставщика: 70% стабильных (малый разброс срока), 30% со смещением и тяжёлым хвостом. Недопоставка оставляет хвост в `gen_internal.backorder` и довозит его отдельным приходом с той же датой заказа.

## Куда править поведение

Ползунки панели лежат в `gen_internal.params`. Формулы шкалы 1–10 — функции `oos_cycle_prob`, `promo_monthly_prob`, `lead_sigma_factor`, `short_prob_factor` в `config.py`. Значение 10 не означает «по всем SKU».

| Что менять | Где |
|---|---|
| Уровень спроса, доля аутсайдеров | `world._build_sku_profiles`, формула `base_daily` |
| Сезон категории, тренд 10% в год | `world.SEASON`, `demand.trend_factor` |
| Ритм и размер заказа клиента | `world.CUSTOMER_RHYTHM`, `demand.order_batch` |
| Каннибализация и доля при OOS | `sales.sell_day`, коэффициент 0.6 |
| Распродажа: длительность, скидка, эластичность | `demand.maybe_start_promo` |
| Возврат брака | `sales._schedule_artifacts` |
| Формула заказа, страховой запас, прогноз | `ordering._order_qty`, `_ses`, `_croston_sba` |
| Заказ новинки | `ordering._novelty_forecast` |
| Сколько SKU ротировать | параметр `rotation_per_month`, логика в `assortment.rotate` |
| Свой заказ вместо автозаказа | `user_orders.calc_orders`. Поставщиков выбирают в панели, список в параметре `user_suppliers` |
| Новый блок дня | функция в `gen/` и вызов в `engine.run` в нужном месте цепочки |

Горячий путь — тысячи SKU на каждый день. Атрибуты SKU и поставщика брать из `world.sku_info`, `world.profile_info`, `world.supplier_info`. История продаж для прогноза — массивы `ordering.History`, окно 120 дней.

## Инварианты

Их стоит проверять после изменений `sales` и `receipts`:

- `rest_qnty` не отрицательный;
- положительные продажи дня не больше остатка на начало этого дня;
- `rest_qnty` сегодня = вчера − продажи + приход (отрицательная продажа — это возврат, он увеличивает остаток);
- у каждой строки `income_day` есть заказ с тем же поставщиком, SKU и `income_order_dt`.
